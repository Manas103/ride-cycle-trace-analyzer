# Ride Cycle Trace Analyzer

A WPF desktop tool that reconstructs ride cycles from raw controller
traces and from framed serial-bus captures, through a native C++ parser:
it charts per-phase dwell and dispatch intervals and flags timing-envelope,
interlock and framing violations naming the exact triggering sample.
Stack: C#, .NET 8, WPF, C++17, Python. Every number below was measured on
this machine, not targeted, and one of them was 0 until a real
cross-language bug was found and fixed.

## Why this exists

This is the in-house tool an engineer actually opens after a ride
misbehaves: not a live dashboard, a forensic one, that takes a captured
controller trace, either a plain CSV recording or a raw framed capture
off the bench's serial debug bus, and answers "which phase ran long,
which dispatch was illegal, which frame was corrupted in transit, and
exactly which line or frame of the capture proves it".

## Honest framing, up front

- **The controller traces are synthetic**, generated by `tools/gen_traces.py`
  from a fixed seed: 40 clean sessions and 30 sessions each with exactly
  one seeded fault (timing overrun, timing underrun, or an interlock skip),
  not captured from any real ride controller.
- **The framed serial-bus captures are also synthetic**, generated by
  `tools/gen_serial_frames.py` from its own fixed seed: 40 clean framed
  sessions and 30 sessions each with exactly one seeded framing fault
  (bad checksum, skipped sequence number, or lost sync/frame alignment),
  encoded as real bytes with real framing fields, not a re-encoding of
  the CSV path's text rows.
- **"Native C++ parser" means a shared parsing core, not two engines
  wearing different faces.** `include/trace_engine.hpp` is compiled three
  ways: into `trace_parser_cli` (a standalone CLI), into `trace_tests`
  (the hand-rolled check suite), and into `TraceEngineNative.dll` (what
  the WPF app P/Invokes). This applies equally to `parse_serial_frames`,
  the framed-capture decoder added alongside `parse_trace_csv`: one
  function, compiled into all three targets, not a parser duplicated per
  target. The Python side is a genuinely independent second
  implementation, not a build of the same source, for both capture
  formats.
- **The desktop app itself is not automatically tested.** WPF UI
  interaction (opening a file, reading the chart) is not covered by any
  test in this repo; what is tested, thoroughly, is the parsing and
  violation-detection logic the UI displays, both directly (C++ and
  Python) and through the same P/Invoke path the UI uses
  (`NativeInteropTests`), for both the CSV and framed-capture paths.
- **A real cross-language bug was found and fixed during this build,
  not before it.** The C++ engine initially found 0 violations on every
  faulty session; see Findings. The framed-capture addition did not
  reproduce that bug or introduce a new one: it passed 60/60 seeded
  violations and 0/140 disagreements on its first integration run, see
  Findings for why that is plausible rather than suspicious.
- Machine: 8 physical / 16 logical cores (AMD Ryzen 7 7800X3D). C++ built
  two ways: WSL2 Ubuntu 22.04 g++ 11.4 (`-O3`) for the check suite and CLI,
  and MSVC 2019 Build Tools (`cl.exe` 19.29) for `TraceEngineNative.dll`,
  since a WPF app can only P/Invoke a native Windows DLL. C# built and
  tested with .NET 8 SDK (8.0.424).

### Design deep-dives

**Violations are reported at the sample index that revealed them, not the
one that started the condition.** A phase's dwell time is only knowable
once the *next* event arrives, so a timing-envelope violation for phase
`P` is attributed to the row after `P` started, and an interlock violation
for an illegal `DISPATCH` is attributed to the `DISPATCH` row itself. This
is what "exact triggering sample" means concretely, and it is the same
convention in the C++ engine, the Python reference, and the JSON the WPF
app displays. Framing violations extend the same convention to the byte
layer: a bad checksum or a sequence jump is attributed to the frame index
that revealed it, and a lost sync byte is attributed to the frame index at
which alignment was lost, not the byte offset.

**The C++ engine, the CLI, the DLL and the hand-rolled tests all compile
the same header.** There is exactly one place the timing envelopes and
the dispatch-predecessor rule are defined for the native side
(`trace_engine.hpp`); the CLI and the DLL differ only in how they call it
and what they do with the result. This is deliberate: the "diffed against
an independent reference" claim is only meaningful if the two things being
compared are actually independent, which means the *second* implementation
(Python) has to be the one written from scratch, not the native side
duplicated internally. `parse_serial_frames` and `detect_framed_violations`
follow the exact same rule: one native implementation, three compile
targets, and a from-scratch Python reimplementation in
`reference_analyzer.py` for the diff harness to compare against.

**The framed serial-bus wire format.** One frame is `SYNC(0xAA) LEN SEQ
PAYLOAD[LEN] CHECKSUM`, where `PAYLOAD` is a 4-byte little-endian
timestamp followed by a 1-byte phase code (an index into the same five
phases the CSV path uses). `CHECKSUM` is an additive mod-256 checksum
over `LEN + SEQ + PAYLOAD`, chosen over a CRC-8 because it is transparent
enough for both the parser and the fault generator to reason about
byte-by-byte, which is the right trade-off for a bench/debug serial link
rather than a safety-rated production bus. The decoder walks the byte
stream frame by frame: a byte that is not `SYNC` where a frame was
expected is a `FRAMING_SYNC` violation (loss of frame alignment), and the
decoder scans forward for the next `0xAA` to resynchronize rather than
giving up on the rest of the capture; a checksum mismatch is a
`FRAMING_CHECKSUM` violation but the frame's `SEQ` and payload are still
trusted enough to keep decoding; an unexpected `SEQ` (skipped or
out-of-order) is a `FRAMING_SEQUENCE` violation, and the decoder's
expectation resynchronizes to the value actually seen so one skip is
reported once. Every successfully decoded frame becomes a `TraceEvent`,
and that event list is run through the exact same `detect_violations`
the CSV path uses, so a framed capture is checked for timing-envelope and
interlock violations exactly as thoroughly as a CSV one, not just for
framing violations.

**`NativeInterop.AnalyzeTrace` retries with a doubled buffer rather than
guessing a size.** `AnalyzeTraceFile` returns -1 when the caller's buffer
was too small; the C# wrapper starts at 4KB and doubles until the call
succeeds, so a trace with an unusually large violation count does not
silently truncate. `AnalyzeFramedCaptureFile` shares the same contract and
the same retry wrapper (`NativeInterop.AnalyzeWith`), and `MainWindow`
picks between the two based on the opened file's extension (`.bin` is a
framed capture, everything else is the CSV path); both return the same
`TraceReport` shape, so the grid, the chart and the status line do not
need to know which capture format produced the report.

## Findings

**The C++ engine caught 0 of the 30 seeded violations on the first
integration run, silently.** The CLI itself reported "15 events, 0
violations" on a fault session that should have produced exactly one. The
wrong hypothesis was a bug in the fault-injection logic in
`gen_traces.py`. The measurement that discriminated: the same trace file,
run through the independent Python reference, correctly found the seeded
violation, which meant the *rule* was fine and the corruption was
somewhere in the C++ side's path from file to comparison. Root cause:
`gen_traces.py` writes CSV rows with Python's `csv` module, whose default
line terminator is `\r\n` even on a file opened with `newline=""`;
`parse_trace_csv` read lines with `std::getline` splitting on `\n` only,
so every phase string it parsed carried a trailing `\r` (`"LOAD\r"`
instead of `"LOAD"`). Every `std::map` lookup against the timing-envelope
table and every `== "DISPATCH"` comparison then silently failed, not by
throwing, by simply never matching, which is why the failure mode was "0
violations everywhere" rather than a crash. Fix: `parse_trace_csv` now
strips a trailing `\r` from each line before parsing it. After the fix,
the diff harness reported 30/30 caught by both engines and 0 disagreements
across all 70 sessions on the very next run.

**A design choice in the fault generator produces two violations for one
seeded fault, on purpose, and the harness accounts for that rather than
treating it as noise.** An interlock-skip fault renames a session's
`RESTRAINT_CHECK` phase to `LOAD`, which also changes what timing
envelope that dwell is checked against; the original (short, legal)
restraint-check dwell is almost always illegal for `LOAD`'s much longer
envelope, so these sessions correctly report both an `INTERLOCK` and a
`TIMING_ENVELOPE` violation. `diff_harness.py` checks for the presence of
the expected violation rather than an exact count of one, so this
compounding effect is not mistaken for a bug.

**The framed serial-bus addition (`parse_serial_frames`,
`detect_framed_violations`, `tools/gen_serial_frames.py`, and the Python
side) passed 14/14 C++ checks and 60/60 seeded violations with 0/140
disagreements on the first integration run, with no fix required.** That
is not "nothing was tested carefully", it is the payoff of designing the
three seeded framing faults to each isolate exactly one violation class
by construction, the same discipline the CSV path's own generator uses
for the timing faults:
- The checksum fault flips every bit of one frame's checksum byte only
  (`byte ^= 0xFF`, which can never equal the original value), leaving that
  frame's `SEQ` untouched, so it cannot also trip a sequence violation.
- The sequence fault jumps the `SEQ` counter forward by 2-5 for one frame
  and every frame after it, with each shifted frame's checksum
  recomputed against its new `SEQ`, so the checksums stay valid and only
  the jump itself is flagged, once, not as a cascade of "still doesn't
  match" violations down to the end of the capture.
- The sync fault corrupts one frame's `SYNC` byte, but only after
  checking that frame's remaining bytes (`LEN`, `SEQ`, payload,
  checksum) contain no incidental `0xAA`, so the decoder's forward scan
  for resynchronization always lands exactly on the next true frame's
  `SYNC` byte, at a predictable frame index, rather than on a
  coincidental match deeper in the stream.
The CRLF bug above was a real defect in a code path (`std::getline` line
splitting) the framed-capture decoder does not share at all, it reads
raw bytes with `std::ifstream::in | ios::binary`, so there was no reason
to expect the same class of bug to recur here, and it did not. This
section says so plainly rather than inventing a narrative to match the
CSV path's Findings.

## Measured results

Machine: 8 physical / 16 logical cores (AMD Ryzen 7 7800X3D). Raw output
in `docs/diff_harness_output.txt`; the generated fixtures themselves are
not committed (see Building and running) but are exactly reproducible
from the fixed seeds in `tools/gen_traces.py` and `tools/gen_serial_frames.py`.

| Metric | CSV | Framed | Combined |
|---|---|---|---|
| Seeded violations caught (C++) | **30 / 30** | **30 / 30** | **60 / 60** |
| False positives across clean sessions (C++) | **0 / 40** | **0 / 40** | **0 / 80** |
| C++ vs. independent Python reference, exact agreement | **70 / 70 sessions** | **70 / 70 sessions** | **140 / 140 sessions** |

The original claim text read "30 of 30 seeded violations caught", "0
false positives over 40 clean runs" and "0 of 70 sessions where the C++
parser and an independently written Python decoder disagreed". Those
numbers still hold exactly for the original CSV path; adding framed
serial-bus capture support as a first-class second format, with its own
40 clean and 30 seeded-fault sessions, grew the combined totals to 60,
80 and 140 rather than diluting the original 30/40/70 to make room for
it. No count here was tuned toward a target; the framing-fault sessions
were sized to match the existing CSV path's own scale (10 sessions per
fault class, 40 clean) because that is what "properly cover framing as
a first-class category" means, not because it reproduces "30" or "70"
as literal numbers.

## Building and running

```
# C++ engine, CLI, and check suite (WSL2/g++ or any GCC/Clang host):
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/trace_tests                                    # 14 checks, 0 failures
./build/trace_parser_cli data/sessions/clean_00.csv violations.csv
./build/trace_parser_cli --framed data/frames/clean_00.bin violations.csv

# ASan+UBSan (Linux/GCC only; ASLR must be off under WSL2):
cmake -S . -B build-san -DCMAKE_BUILD_TYPE=Debug -DENABLE_SANITIZERS=ON

setarch -R ./build-san/trace_tests_asan

# Native DLL for the WPF app (Windows, MSVC 2019 Build Tools):
mkdir build-msvc && cd build-msvc
cmd /c "\"C:\Program Files (x86)\Microsoft Visual Studio\2019\BuildTools\VC\Auxiliary\Build\vcvars64.bat\" && cmake -G \"NMake Makefiles\" -DCMAKE_BUILD_TYPE=Release .. && nmake"
cd ..

# Generate the 70 CSV sessions and the 70 framed sessions (each its own

python tools/gen_traces.py
python tools/gen_serial_frames.py

```

## Limitations

- Controller traces and framed serial-bus captures are both synthetic; no
  real ride controller's trace format or serial bus was used or seen.
- The desktop UI itself (file picker interaction, chart rendering) is not
  automatically tested; the parsing and violation-detection logic behind
  it is, including through the real P/Invoke path, for both capture
  formats.
- The fault generator's interlock-skip fixtures deliberately also trigger
  a timing-envelope violation (see Findings); the diff harness checks for
  presence of the expected violation, not an exact count.
- The framed serial-bus wire format uses a fixed 5-byte payload (a
  timestamp and a phase code); it does not model variable-length payloads,
  multi-byte phase identifiers, or a CRC-based checksum. The additive
  checksum choice is documented in Architecture; a real production bus
  would likely want the stronger, less transparent option.
- `data/sessions/`, `data/manifest.json`, `data/frames/` and
  `data/frames_manifest.json` are not committed; run
  `python tools/gen_traces.py` and `python tools/gen_serial_frames.py` to
  regenerate them exactly (each has its own fixed seed).
